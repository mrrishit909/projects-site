## 1. User stories and acceptance criteria
1. **As a data governance analyst** I open the scorecard and see, for the as-of 2026-10-05T00:00:00Z, each dataset's five dimensions apart, its weighted score under the weight version named, and the critical override beside it.
   *Accept:* `ds-customers` shows 0.990175 (w2) and 0.990329 (w1) with the override set because its critical key rule fails on 2 rows and one critical issue is open; the figures equal the independent reference SQL and the Python domain (investigation 01; the reconciliation of `sql-analysis.md` section 11: 175 rows equal).
2. **As a data quality analyst** I see the known answer reproduced before any volume: 95 of 100 complete (0.950000); validity 90 of 95 populated-only (0.947368) and 90 of 100 over all eligible rows (0.900000), both labelled; a critical key failure visible although the weighted score is above 0.95.
   *Accept:* equal in the Python domain, the SQL reference, the TypeScript domain, the standard-library oracle `tests/reference_check.py` (ALL OK, 805 checks, recorded in the ledger), `expected.json` and the workbook's `Golden case` sheet.
3. **As an accountable owner** I can tell which datasets have no accountable owner and what they carry: 5 of 40 datasets (coverage 0.875000), 66 unresolved issues.
   *Accept:* `test_designed_inactive_owners_leave_five_datasets_uncovered`, `test_ownership_coverage_inactive_owner_uncovered_and_time_of_deactivation_matters`, investigation 02.
4. **As a data quality analyst** I never see a claim counted as a resolution: an issue is resolved only after a successful rerun of the same rule version.
   *Accept:* `test_a_close_without_a_rerun_is_claimed_and_never_resolved`, `test_the_database_refuses_resolved_without_a_successful_rerun_of_the_same_rule_version`, `test_c10_resolves_only_after_a_successful_rerun_of_the_same_rule_version`; 315 resolved, 99 claimed, 160 open (investigation 04).
5. **As a steward** I approve or reject a merge only as a person other than the proposer, and can reverse an approval with both identities restored and the history kept.
   *Accept:* `test_c07_a_proposer_cannot_decide_their_own_candidate_and_the_refusal_is_kept`, `test_c08_reverses_a_merge_restoring_both_identities_and_keeping_history`; precision 172 of 174 (0.988506) from the verification layer, outside the matcher (investigation 07).
6. **As a data engineer** I see which lineage is declared, which observed and which only inferred, and that an inferred edge never counts as observed: 0.725000 (58 of 80).
   *Accept:* `test_lineage_coverage_is_over_distinct_pairs_and_inferred_is_never_observed`, investigation 05.
7. **As a data governance analyst** I can see what a weight change did without any rule change: 13 of 29 scored datasets differ, 7 by at least 0.005.
   *Accept:* `test_designed_weight_change_moves_scores_without_a_rule_change`, `test_the_weight_version_changes_the_score_and_is_named_in_the_result`; investigation 03.
8. **As a decision owner** I get an ordered list of unresolved issues with the accountable owner of each and the rule that ordered it.
   *Accept:* investigation 10 and `executive-memo.md`; the rule (severity, then inactive owner, then age) is stated, not hidden.
9. **As an analyst** I can rebuild the headline measures from CSV exports and compare them with the independent recomputation.
   *Accept:* the measures recomputed from `artifacts/bi/*.csv` equal `reference_metrics.sql` and the domain (`bi-package.md`).
10. **As a reader of the evidence** I see what is built, what is simulated in browser memory and what the review found and fixed.
    *Accept:* the case-study route, `technical-case-study.md`, `uat-evidence.md` and this file say so (section 5).

## 2. Functional requirements
| ID | Requirement | Entities, metrics, commands |
|---|---|---|
| FR-01 | Register a dataset only with an active owner and a classification; a monitored dataset declares zone, local time and grace | `datasets`, `owners`; C01 `register-dataset`; P07-FLOW-01 |
| FR-02 | Publish a definition draft -> reviewed -> published, each step a new version row with a change record; the reviewer is not the drafter; a published definition is never rewritten | `metric_versions`, `definition_changes`; C02 `publish-definition`; P07-FLOW-02 |
| FR-03 | Run an active rule: eligible and failing counts, the rule version and the weight version; compare with the previous run only under the same rule version | `rule_runs`; C03 `run-rule`; P07-FLOW-03 |
| FR-04 | Open an owned issue on a failing scheduled run with the rule's severity | `issues`; C04 `open-issue`; P07-FLOW-04 |
| FR-05 | Triage: investigate (owner and due date), claim (a close without a rerun) and reopen (a cycle); `detected_at` is kept | `issues`, `issue_events`; C05 `triage-issue`; P07-FLOW-05 |
| FR-06 | Suggest a match as a canonical-order candidate with score, features and an explanation; never a merge | `match_candidates`; C06 `suggest-match`; P07-FLOW-06 |
| FR-07 | Approve or reject a merge by a reviewer other than the proposer; the right record maps to the left | `merge_decisions`; C07 `approve-merge`; P07-FLOW-07 |
| FR-08 | Reverse a merge with a reason: both identities restored, history kept | `merge_decisions`; C08 `reverse-merge`; P07-FLOW-08 |
| FR-09 | Disable a rule with a reason and a date: runs and issues stay, open issues stay open | `quality_rules`; C09 `disable-rule`; P07-FLOW-09 |
| FR-10 | Verify a remediation by rerunning the rule over the issue's records: a passing rerun of the same rule version resolves it, anything else leaves it claimed | `rule_runs`, `issues`; C10 `verify-remediation`; P07-FLOW-10 |
| FR-11 | Correct rows and record a refresh as append-only versions (D-10 R7-07) | `dataset_rows`, `dataset_refreshes`; C11 `correct-dataset-rows`, C12 `record-refresh` |
| FR-12 | Compute the twelve metrics for any as-of, half-open window, weight version and grouping (dataset, owner, source system, severity) | `GET /metrics`; P07-MET-01..12 |
| FR-13 | Read every entity with stable ordering, an opaque cursor and whitelisted filters, plus comparable runs, identity map, rule versions and refreshes | `GET /data/{entity}` and the four named reads |
| FR-14 | Serve the published snapshot as a static interactive site that reproduces the golden case and the derived views in the browser, with no write | Mode B: `web/` |
| FR-15 | Provide an independent SQL recomputation of every metric and reconcile every artifact number to it | `data/sql/reference_metrics.sql`, `data/sql/analysis/` |
