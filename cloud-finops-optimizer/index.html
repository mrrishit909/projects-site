What Did the Rightsizing Really Save?

FinOps for an invented six-account estate on three clouds: an SLO-aware rightsizer opens 72 changes worth $19,825 a month where a 14-day average rule would make 116 with 67 expected SLO breaches, a mixed-integer programme sizes the commitments for the smaller estate, a second person opens the Terraform pull request, and four weeks later the verifier measures $17,466 saved against $17,698 true, where before/after claims $25,084.

Built from a written blueprint as one vertical slice. The clouds are simulated: six accounts, their workloads, prices and bills come from a generator in the repository, and pull requests and purchases are "shipped" by telling the generator, which is what lets every recommendation and every verified dollar be checked against the truth. No real cloud account or billing data is used and nothing is ever applied to infrastructure. Not built: real cloud connectors, three-year terms and spot, a deep forecaster, Kafka, ClickHouse, single sign-on.

01The problem

Cloud cost tools are good at telling a team that a machine averages 7% CPU and bad at saying whether shrinking it will hurt: the average hides the nightly batch, the month-end close and the workload that grows every week. Commitments make it worse, because committing before rightsizing locks the waste in and committing after it to last month's usage over-buys, and when the changes ship in the same month as the savings plan nobody can say which saved what. Can software recommend only the changes the forecast says the SLO will survive, size the commitments for the estate that remains, change nothing without a reviewed pull request, and then prove what was saved in a way that would survive an audit?

Blueprint 5 of twenty in a fourth build book, built as its demo scenario end to end.

02What I built

A Python service on PostgreSQL with a background worker and a web page, started by one docker compose up.

  • A simulated multi-cloud estate: six accounts on AWS, Azure and Google Cloud with machines, autoscaled Kubernetes node pools, databases and volumes; hourly demand with daily and weekly shape, growth and spikes; a price catalogue and CUR-style billing with savings plans and reservations.
  • Connectors that accept only role references, an inventory with a 15-minute freshness policy, and a cost explanation that splits any change into usage, configuration, rate, new and removed resources.
  • A forecast and an SLO-constrained rightsizer with a change-risk model trained on the estate's own history, against the 14-day average rule.
  • A commitment portfolio by mixed-integer programming over forecast scenarios, and an SLO-risk simulation of alternative plans.
  • Terraform pull requests a second person opens, never applied by the service, and a savings verifier scored against the simulator's truth.

03How it was built

  1. 01

    Demand belongs to the workload

    Each workload's demand is drawn from its own daily and weekly shape, growth and noise, keyed by resource and day; a machine's size only changes how full it looks and what it costs. The generator knows which machines are idle, oversized, bursty, month-end jobs, growing or memory-bound, and which volumes are attached only for a Sunday restore test; the service sees only utilisation, units and bills. That is what lets a period be re-run with and without a change on the same demand.

    d = vref * r["level"] * _shape(r["trough"]) * week * growth * noise
...
cpu_u[i] = np.where(units[i] > 0, np.minimum(cpu_d[i] / v, 1.0), 0)
  2. 02

    Size to the forecast's p99, not the average

    Every workload is forecast four weeks ahead (an hour-of-week profile, a weekly trend, whole days of residuals bootstrapped into 100 paths), and a resize is the smallest size whose p99 CPU stays under 80% and memory under 85% in 90% of paths. On three held-out estates the forecast's WAPE was 0.076–0.079 against 0.113–0.127 for last week repeated, and the true p99 fell under its 90% path p99 90.4–91.0% of the time. The 14-day average rule shrinks the nightly batch, the month-end job and the growing service alike.

  3. 03

    Commit to the estate that will remain

    Savings plans per cloud in $1-an-hour blocks and reservations per database type are chosen together by a mixed-integer programme over 20 scenarios of the next 13 weeks, after the planned rightsizing. Per pool it is a newsvendor problem; whole blocks and a shared budget make it a packing one. Committing to last month's minimum, the common rule, buys for usage the rightsizing removes.

    c = solver.Constraint(float(u), solver.infinity())      # o + block * n >= u
c.SetCoefficient(o, 1)
c.SetCoefficient(n, block)
  4. 04

    A pull request, never an apply

    Open recommendations become unified Terraform diffs per account repository and a pull request carrying the evidence, risk and rollback. The service has no write path to any cloud; a request to apply directly is refused by policy, risky or stale recommendations become review tasks, and the engineer who proposed the change cannot approve it.

    if body.apply and not pol["allow_direct_mutation"]:
    raise Problem(403, "direct_mutation_disabled", ...)
...
if cr["proposed_by"] == ctx.actor_id:
    raise Problem(403, "proposer_cannot_approve", "a change to infrastructure needs a second person")
  5. 05

    Count the margin, not the average rate

    Under a fixed savings plan, usage removed above the commitment saves full on-demand price and usage removed inside an under-used one saves nothing. So the verifier rebuilds hourly spend for every pricing pool, puts the old configurations' cost back, and bills each pool again through the commitments in force. Before/after counts the new commitments' discount as rightsizing; difference-in-differences prices the savings at the average rate.

    def pool_bill(E, C, d):
    return float((C * (1 - d) + np.maximum(E - C, 0)).sum())
...
saved[g] = (pool_bill(E + D, C, d) - pool_bill(E, C, d), float(D.sum()))

The blueprint's bars were a false-positive rate under 10% and an attribution error under 5%; inventory freshness under 15 minutes is enforced (stale accounts become review tasks) and an incremental sync of all six accounts took 72–117 ms.

Honest limits. Zero false positives come from caution: the rightsizer sizes to the 90th percentile of the forecast's p99 and the breach line sits 10 points above its target, and in the demo an aggressive plan takes $22,818 a month instead of $19,825 at 1.83 expected breaches. The change-risk model barely beats the headroom the rightsizer already uses (in the demo, headroom alone scored 1.000). The service's model of the autoscaler is cruder than the simulated one, so the portal pool's floor drops only from 10 to 9. The verifier re-prices with the same catalogue and allocation rule the simulator bills by, so under 2% is a best case; a real bill adds credits, private discounts and amortisation. Commitments are scored on 13 weeks of a one-year term.

Checks. 13 tests, including: demand does not change when a machine is resized, the verifier's pool billing equals the simulated bill, the forecast recovers a 5% weekly trend, the rightsizer leaves a nightly batch, a growing service and a memory-bound machine alone while the average rule shrinks them, the MILP commits at the newsvendor quantile and beats a greedy plan under a budget, a key pasted as a credential is refused and never stored, the proposer cannot approve, an approved pull request changes no inventory, a stale account's recommendations become review tasks, and one company cannot see another's resources. The Docker stack was run end to end.

05What I'd do next

  • Real billing exports and cloud APIs behind the same connector interface, with the verifier checked against a real invoice's credits and amortisation.
  • A model of the autoscaler learned from each pool's own scaling history, so node-pool floors can come down as far as the demand allows.
  • Three-year terms and convertible commitments, scored on a longer horizon with churn and migration risk.
