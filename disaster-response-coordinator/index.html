Who Gets Cut Off, and Who Gets Help First?

A hurricane command system on an invented coastal county: it forecasts which neighbourhoods will lose every road to a hospital, turns citizen reports into incidents, and assigns all 24 response units at once. At peak surge it reached 18 of 35 severe emergencies where sending the nearest unit in call order reached 14.

Python · FastAPI · PostgreSQL 16 (row-level security) · Monte Carlo risk model · Assignment solver (SciPy) · Linear programming (HiGHS) · scikit-learn · Docker Compose · 87 testsRun the seven-step demo ↗Code on GitHub ↗

Built from a written blueprint as one vertical slice, on a simulated county and storm: the map, the people, the surge and every citizen report are generated, so each part can be checked against a known answer. The surge is a simple formula, not a real storm-surge model. No alert is ever sent: alerts are stored only. Not built: live weather and road feeds, satellite image analysis, PostGIS, Kafka, Terraform, single sign-on.

01 — The problem

When a hurricane comes ashore, an emergency operations centre has too many calls and too few boats and ambulances, on a road network that is changing by the hour. Dispatchers usually send the nearest free unit to each call as it comes in. Can software forecast which neighbourhoods will be cut off before it happens, and get more of the serious emergencies reached with the same units?

Blueprint 1 of ten in a second build book, built as its demo scenario end to end.

02 — What I built

A Python service on PostgreSQL with a map page, started by one docker compose up.

  • Risk forecast: the chance each neighbourhood has no open road to a working hospital.
  • Shelter allocation: who goes to which shelter, within capacity, with the least total driving.
  • Report intake: sorts citizen reports, merges repeats of the same emergency, files noise.
  • Dispatch: assigns every unit to every open incident in one solve, over the roads still open.
  • Storm simulator: stands in for live feeds, so the forecast can be scored against what then happens.

03 — How it was built

  1. 01

    Replay the storm 300 times

    Two things are uncertain before landfall: how high the surge will be (4.5 m, give or take 0.7) and the elevation survey (off by about 0.25 m). So the storm is replayed 300 times with both varied. In each replay, flooded roads and bridges are removed and the road network is checked: can this neighbourhood still reach a working hospital? The share of replays where it cannot is its risk. This catches something a flood line misses: blocks that stay dry but are surrounded.

    peak, e = rng.normal(mean, sd), elev + rng.normal(0, SURVEY_ERROR, N)
iso += isolated(w, world.closed(w, peak, target_hour, e), hospitals)
  2. 02

    One emergency, four reports

    Each report is sorted into water rescue, medical, fire, utility or noise. A report of the same type from the same block joins the incident already open and raises its confidence; a single social-media post is not enough to send a unit. Merging is a real tradeoff: merging across neighbouring blocks hid a third of the real incidents inside others, so this build merges within a block only and accepts some duplicates.

    def corroborate(confidence, credibility):
    return 1 - (1 - confidence) * (1 - credibility)
  3. 03

    Assign every unit in one solve

    For every unit and every incident the travel time is computed over the roads open right now (boats can cross flooded roads slowly; ambulances cannot). Then one exact solve picks the pairing with the lowest total of severity squared times travel time. Each incident also has a "nobody comes" option costed at two hours, so when units run out it is the least severe that wait.

    cost[:, :m] = wt[:, None] * eta
cost[np.arange(n), m + np.arange(n)] = wt * UNSERVED_S
rows, cols = linear_sum_assignment(cost)
  4. 04

    Break something on purpose

    In the demo the ambulance on the most severe call reports itself out of service. Its incident goes back to the queue and the plan is solved again: 4 units are redirected and 18 keep their call. A database rule makes it impossible for one unit to hold two live dispatches, and a retried request replays its first answer instead of dispatching twice.

    CREATE UNIQUE INDEX dispatches_one_job_per_unit
  ON dispatches (resource_id) WHERE status = 'en_route';
  5. 05

    Score the forecast against what happened

    Because the storm is simulated, the forecast made at hour 0 can be checked at hour 6. The real surge came in at 4.9 m, higher than forecast: 36 neighbourhoods were cut off, the forecast had flagged 29 of them and raised no false alarm. Across 200 other simulated storms its error score was 0.027, against 0.037 for a plain flood-line rule.

The forecast error is a Brier score (lower is better) over 200 storms; the simple way is "below the forecast water line".

Shelters. 29 neighbourhoods (53,464 people) were told to leave. With an assumed 12% needing a public shelter, 4,300 were placed and 2,115 had no place. The system reports that gap instead of hiding it.

Checks. 87 tests, including: the solver never doing worse than call order on 40 random cases, shelter capacity never exceeded, a retried report not counted twice, and one county unable to see or reset another's data.
