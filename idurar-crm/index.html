Dovecote: a support desk where clients see only the answer

A small support desk where the client sees the answer, and only the answer.

01 — The problem

A small team handles client requests with minimal setup, but the people filing them must see the answers and never the team's internal notes, and nobody should be able to move a ticket that is not theirs.

Defining workflow: A requester files a ticket, a manager assigns it, an agent creates a linked task and an internal note and resolves it. The requester sees the public reply and the resolution but cannot retrieve the internal note through any endpoint.

02 — What I built

One of eleven independent CRM MVPs in a single monorepo, each with its own database, migrations, tests and review packet. This one is inspired by iDURAR and is called Dovecote.

  • Ticket states (open, in progress, waiting, resolved, reopened) with a defined actor for each change, enforced by the service and by a database trigger, with every change recorded
  • Public replies versus internal notes: a requester can never write or read an internal note, tested by scanning every requester-reachable response
  • An authenticated requester portal that shows only the requester's own tickets, the public thread and the resolution
  • Tasks linked to tickets, a My work screen with overdue indicators, per-person workload and manager-only role administration
  • Append-only assignment and status history, idempotent filing and replies, gapless ticket numbers under concurrency

03 — How it was built

  1. 01

    Specify before building

    An acceptance document names the persona, the bounded scope, what is deferred, and ties every required feature to evidence (a test, an end-to-end journey or a recorded check).

  2. 02

    Model the database so the rules hold even if the code is wrong

    A Prisma schema plus a hand-written migration of CHECK constraints, composite foreign keys that pin every record to its workspace, and triggers. The tests try to break these from raw SQL.

  3. 03

    Build the distinguishing workflow through every layer

    Ticket states (open, in progress, waiting, resolved, reopened) with a defined actor for each change, enforced by the service and by a database trigger, with every change recorded

  4. 04

    Prove it in a fresh clone

    20 gate checks pass and 0 fail in a fresh clone of commit bf0b91ff8a: 2 unit, 39 integration against a real PostgreSQL, 22 browser tests on the production build, container start, a live black-box check, restart persistence, backup and restore, and a production-dependency audit.

  5. 05

    Review it as an independent reader would

    A review packet lists what is implemented, what is measured, what was fixed on the way, and every known limit and release blocker, so nothing here is claimed beyond its evidence.

05 — What I'd do next

  • No email in or out, no attachments, no SLA calendars (a due time is hours from filing; waiting only suppresses the overdue flag)
  • No merging, categories, custom fields or notifications; staff see all tickets and clients
  • A requester account belongs to one client and is created by an operator
  • Not production-ready: no TLS, proxy or monitoring provisioned
