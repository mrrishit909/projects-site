01 / The problem

An administrator wants to define collections and fields without editing code or running migrations, and get forms, lists, filters and validation automatically, safely.

Defining workflow: Build an Assets collection with serial number, status, purchase date and a company relation, create and edit records immediately, make a field required against existing data (refused with the offenders, then backfilled), and confirm another workspace cannot see any of it.

02 / What I built

One of eleven independent CRM MVPs in a single monorepo, each with its own database, migrations, tests and review packet. This one is inspired by NocoBase and is called Loom.

  • Runtime collection builder: text, number, date, boolean, select and relation fields with required, default and validation settings
  • Record forms, lists, filters, saved views and API validation generated from one shared set of field rules
  • Relations stored as separate rows with database-enforced integrity (RESTRICT or CLEAR on delete)
  • Validated schema evolution (never lossy), append-only schema revisions, collection-level permissions, safe identifiers and limits

03 / How it was built

  1. 01

    Specify before building

    An acceptance document names the persona, the bounded scope, what is deferred, and ties every required feature to evidence (a test, an end-to-end journey or a recorded check).

  2. 02

    Model the database so the rules hold even if the code is wrong

    A Prisma schema plus a hand-written migration of CHECK constraints, composite foreign keys that pin every record to its workspace, and triggers. The tests try to break these from raw SQL.

  3. 03

    Build the distinguishing workflow through every layer

    Runtime collection builder: text, number, date, boolean, select and relation fields with required, default and validation settings

  4. 04

    Prove it in a fresh clone

    20 gate checks pass and 0 fail in a fresh clone of commit 19ed093e9a: 2 unit, 35 integration against a real PostgreSQL, 14 browser tests on the production build, container start, a live black-box check, restart persistence, backup and restore, and a production-dependency audit.

  5. 05

    Review it as an independent reader would

    A review packet lists what is implemented, what is measured, what was fixed on the way, and every known limit and release blocker, so nothing here is claimed beyond its evidence.

05 / What I'd do next

  • Collections are logical: records are JSONB rows in one table, never SQL tables
  • Range filters, contains and field sorting have no dedicated index (no DDL privilege at runtime); bounded by 100,000 records per collection and not benchmarked at that limit
  • No unique constraints, many-to-many, computed fields, files or import/export
  • Not production-ready: no TLS, proxy or monitoring provisioned
