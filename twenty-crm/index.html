Kestrel CRM: a pipeline that stays out of your way

A CRM that stays out of your way: fast tables, a command palette, an API for everything.

01 — The problem

A small sales team wants a fast, keyboard-friendly CRM whose every record is also available through a clean API and signed webhooks.

Defining workflow: Create a company and contact through the REST API, find them in the UI, move a deal with the keyboard, and see exactly one signed webhook delivery with its attempt log; revoke the API key and the access stops.

02 — What I built

One of eleven independent CRM MVPs in a single monorepo, each with its own database, migrations, tests and review packet. This one is inspired by Twenty and is called Kestrel CRM.

  • Split-pane tables with inline editing, command palette, fast search and saved filters
  • Versioned /api/v1 REST with schema validation, cursor pagination, filter allowlists and generated OpenAPI
  • Scoped, revocable API keys stored as hashes (shown once)
  • Signed webhook delivery through a durable outbox with retries and an attempt log; outbound targets restricted against SSRF
  • Owner and member roles, member administration

03 — How it was built

  1. 01

    Specify before building

    An acceptance document names the persona, the bounded scope, what is deferred, and ties every required feature to evidence (a test, an end-to-end journey or a recorded check).

  2. 02

    Model the database so the rules hold even if the code is wrong

    A Prisma schema plus a hand-written migration of CHECK constraints, composite foreign keys that pin every record to its workspace, and triggers. The tests try to break these from raw SQL.

  3. 03

    Build the distinguishing workflow through every layer

    Split-pane tables with inline editing, command palette, fast search and saved filters

  4. 04

    Prove it in a fresh clone

    21 gate checks pass and 0 fail in a fresh clone of commit 55ab57c54c: 9 unit, 59 integration against a real PostgreSQL, 19 browser tests on the production build, container start, a live black-box check, restart persistence, backup and restore, and a production-dependency audit.

  5. 05

    Review it as an independent reader would

    A review packet lists what is implemented, what is measured, what was fixed on the way, and every known limit and release blocker, so nothing here is claimed beyond its evidence.

04 — Results

21 gate checks pass and 0 fail in a fresh clone of commit 55ab57c54c: 9 unit, 59 integration against a real PostgreSQL, 19 browser tests on the production build, container start, a live black-box check, restart persistence, backup and restore, and a production-dependency audit.

Performance (10,000 contacts, local hardware). sequential p95 2.0 to 16.6 ms and concurrent p95 5.6 to 19.3 ms across 13 scenarios; the per-key rate limit was raised for the run

Screenshots on the showcase site are real captures at 1440, 768 and 390 pixels wide, taken from the production build with synthetic data.

05 — What I'd do next

  • Accounts are administrator-managed (no email invitations or recovery)
  • Chromium only; accessibility is automated (axe) plus keyboard reachability, no manual screen-reader pass
  • Not production-ready: no TLS, proxy or monitoring was provisioned or tested
  • Inherited dev-only audit findings and an end-of-life ESLint 9 are documented, not hidden
